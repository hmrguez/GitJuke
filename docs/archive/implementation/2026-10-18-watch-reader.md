## Reader and pagination

The preceding `watch_page` query applied watch membership to a full locator relation, then ordered and used `LIMIT 101 OFFSET`. Reason reads could return every source in one statement. Protected TEMP views added canonical/journal union work before those filters and ordering. A final result limit alone did not bound those paths.

`watch_store.rs::watch_page` now delegates to `watch_reader.rs`. Native stable-ID and per-identity source windows read at most **128 candidates before visibility/membership filtering**, using separate first/successor index seeks. Offset is counted across the visible eligible identity stream in Rust; it is not passed to a deep SQL OFFSET statement. This preserves exact native ID ordering and the existing offset API: **100 returned items**, one additional visible lookahead and `next_offset = offset + returned count` only when more items exist. Rejected invisible/orphan candidates still advance the in-call native cursor. Large offsets do not require an offset-sized collection.

Native signed number/time conversions, nullable head/merge/success values, all membership reasons and their exact BINARY source order remain the previous reader contract. Denial remains a NOCASE repository/number point probe, applied to the visible locator image, with the same `Resource unavailable` label. Reader calls do not change seen state, membership, refresh/access timestamps or history.

SQLite's established negative-bound OFFSET conversion is retained for unsigned values whose existing `as i64` cast becomes negative. Returned-offset arithmetic now fails closed if addition overflows, instead of wrapping/panicking. Normal pagination is unchanged.

## Protected old-snapshot reads

Cached watch-list navigation remains available through interrupted publication; this reader does not block merely because a publication marker exists. It determines old-image versus committed visibility once within its snapshot. Planning/applying/noncommitted phases use retained images; committed/absent markers use canonical state.

For protected reads, journal candidates are scanned in native sequence windows of at most **128 rows before table, old-image, identity or lower-key filtering**. A BTreeSet retains at most 128 old locator/reason keys after the current native frontier. Those keys are merged with the first 128 native canonical keys into at most 128 distinct next candidates. JSON-encoded journal keys are decoded before comparison, so escaped controls, quotes, slashes and Unicode retain native text ordering rather than JSON encoding order. Unrelated, rejected and already-visited journal rows remain bounded per statement; fixed per-call read snapshots make the traversal finite.

Exact `(table,json_array(native key...))` lookups against the existing unique journal index decide each candidate's visibility. A null old image hides a newly inserted canonical row; a retained old image restores a deleted or changed locator/reason; canonical rows without a journal override remain visible. Old-only identities and reasons are included even when their canonical rows are physically absent. This avoids an unbounded UNION/anti-join/filter/sort over the protected TEMP views. No new index, shadow table, migration or persistent reader cursor is introduced.

The same mechanism windows reasons before rejecting hidden additions, and returns every visible reason in the original native order. Metadata/lookahead candidates are decoded before truncating to 100, while full reasons are loaded only for returned items, preserving the reader's scope.

## Snapshot, bytes and mutations

Standalone calls own one SQLite read transaction spanning phase, candidate windows, journal projections, membership, visible row data, reasons, denial labels and returned revision. Existing caller transactions keep their snapshot and ownership. A concurrent visibility commit cannot mix old rows/reasons with a new revision; the next call sees the committed page. A late error discards the whole provisional page and releases an owned snapshot rather than returning a partial list.

The original **900 × 1,024-byte serialized item-array budget** remains inclusive. Empty-reason item serialization establishes the base size; exact serialized reason lengths and commas are charged as reasons are appended, rejecting oversized output early with the unchanged error. The original final serialization guard remains as well. This is an output budget, not a whole-allocator or variable-key-byte claim. Candidate vectors and key sets each hold at most 128 identities, and item/lookahead storage holds at most 101 rows; physical/temp/allocator bounds and whole-value JSON/serialization work remain open.

Reading performs **zero direct row mutations** and adds no bookkeeping against the **128-total-direct-mutation cap**. Schema remains **14**. The inclusive **524,288,000-byte** shared disposable ceiling, retained images/accounting, exact shared LRU order, atomic publication visibility, stable identity, persistent Pause, validators/deadlines and cached navigation retain their contracts. Durable Activity/seen/dedup/progress/baseline/recovery history and terminal attempted/unavailable intent/member/attempt records are unchanged.

The number of windows still grows with offset/cardinality. Protected key discovery can rescan journal windows per locator/reason frontier and per returned identity. No constant/sublinear total read time, bounded cumulative traversal, universal JSON-function CPU bound or native-performance qualification is claimed.
