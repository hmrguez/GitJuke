# Bun migration and test benchmark — 2026-10-18

The project now uses Bun 1.4.2 for dependency installation, JavaScript execution, frontend builds and JavaScript tests. `bun.lock` replaces `package-lock.json`; all 106 locked dependency versions were verified against the original npm lockfile. `packageManager` records the tested Bun version. Tauri hooks, the check script and development instructions now use Bun.

The existing diff tests retain their Node-compatible assertions and `node:test` imports. Renaming `scripts/diff-tests.mjs` to `scripts/diff.test.mjs` makes them discoverable by Bun. `bunfig.toml` limits discovery to `scripts/`, avoiding Cargo build artifacts, and runs JavaScript CLIs with Bun. These settings follow the official [test configuration](https://bun.com/docs/test/configuration) and [Bun runtime configuration](https://bun.com/docs/runtime/bunfig) documentation.

## Commands

```sh
bun install --frozen-lockfile
bun test                  # Two JavaScript tests
bun run test:rust         # cargo test -p gitjuke-core
bun run test:all          # Both suites, stopping on failure
bun run build
bun run check
bun run tauri dev
```

The original `test` script remains a Rust-only compatibility alias: `bun run test` and `npm test` both invoke Cargo. `test:diff` now uses Bun; `test:diff:node` retains the previous Node test command for benchmark reproduction. Node/npm are only required for that comparison.

## Passing JavaScript benchmark

Host: macOS-27.0-arm64-arm-64bit-Mach-O. Bun 1.4.2, Node v25.9.0, npm 11.12.1.

Each command runs the same two tests and imports the same TypeScript source. One excluded warmup per command, then 30 measured invocations each. Commands run sequentially, reversing their order every round, with no concurrent build or Rust test process. Wall time includes process startup, discovery and reporting; output is redirected identically to files. These are warm-cache local results for a small suite, not isolated test-body timings or a projection for larger suites.

| Command | Median wall time | Min–max |
| --- | ---: | ---: |
| `npm run test:diff:node` (previous npm/Node JavaScript workload) | 279.9 ms | 273.0–285.5 ms |
| `node --experimental-strip-types --test scripts/diff.test.mjs` | 179.2 ms | 171.4–184.8 ms |
| `bun test` | 23.0 ms | 22.4–24.6 ms |

Bun takes **12.2× less time** than the npm/Node command (**91.8% shorter**, saving 256.9 ms per invocation). Against direct Node, it takes 7.8× less time. All measured JavaScript runs passed. [Raw samples, versions and commands](evidence/2026-10-18-bun/javascript/results.json).

Reproduce:

```sh
python3 scripts/benchmark-tests.py --js-runs 30 --rust-runs 0 --output /tmp/gitjuke-bun-benchmark
```

The script can also benchmark equivalent Cargo workloads via `npm test` and `bun run test:rust` using `--rust-runs 1` or more. It stops on a failed command instead of treating failed runs as valid benchmarks.

## Original npm test and Rust failures

A literal comparison of `npm test` and `bun test` would compare different suites: the original `npm test` runs Rust, while `bun test` runs JavaScript. Bun's test runner does not replace Cargo.

The original `npm test` exited 101: **222 passed, 3 failed**, with the library runner reporting **275.58 s**, after a 1.93 s compilation. This is the library test duration, not a measured end-to-end process duration. Cargo stopped before integration/doc tests. [Original baseline output](evidence/2026-10-18-bun/npm-test-baseline.log).

The three failures were existing assertions in `crates/gitjuke-core/src/pr_purge.rs`:

- `pr_purge_global_bound_immediate_visibility_and_durable_isolation`: actual 43, expected 25.
- `pr_purge_barrier_later_batch_and_finish_faults_resume`: actual 68, expected 132.
- `pr_purge_sigkill_barrier_and_cleanup_preserve_only_committed_batches`: actual 712, expected 648.

`bun run test:rust -- pr_purge::tests` reproduced all three assertion failures (2 passed, 3 failed). [Bun reproduction output](evidence/2026-10-18-bun/bun-rust-pr-purge.log), [status metadata](evidence/2026-10-18-bun/rust-status.json). Rust sources were not changed by this migration. No Rust suite speedup is claimed; resolving the baseline failures is required before a passing full-suite benchmark.
