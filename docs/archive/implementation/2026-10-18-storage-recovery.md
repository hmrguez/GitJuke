## Implemented behavior

A database startup failure previously propagated out of Tauri setup and terminated the app before recovery guidance could render. A managed startup state now keeps the native window, menus, close/reopen and Quit usable when no Runtime can safely start. The reader remains unmounted. The recovery view explains the protective stop, displays the exact local database location and distinguishes missing, legacy, current-but-failed, newer, corrupt and unreadable inputs. It offers an explicit **Retry storage check**, executed off the native UI thread and serialized against duplicate startup. It creates no reset/export/login/credential flow and does not rename, delete or replace original files.

Retry uses the existing Runtime/Store startup path: transactional upgrades, interrupted-publication completion, cleanup, original-account validation, persistent Pause and server deadlines remain authoritative. There is exactly one managed worker on success. Current-schema storage protection still uses the existing permitted read-only cache path; corrupt or incompatible data never substitutes a successful empty set. The new diagnostic reads open SQLite read-only and run integrity/schema checks; SQL, private payloads and raw errors are not displayed. A negative `user_version` is rejected before schema initialization, preserving the original file instead of treating it as an empty database.

`StorageUsage.transientBytes` is explicitly nullable and currently **null**. Preferences states that SQLite temporary files are unmeasured and measured database/WAL/SHM/journal bytes are a lower bound; 1-GiB warnings can understate peak usage. Unlinked SQLite sort files cannot honestly be counted by listing the application directory. No forced in-memory temp policy, process-global SQLite directory override, full VFS rewrite, whole-database cap or unsupported zero-temp claim was added. Complete transient/peak accounting remains Pending.

- **Filesystem fault environment**: opt-in tests use a separately mounted **64-MiB HFS+ sparse disk image** at `/private/tmp/gitjuke-storage-fault-volume`. They require an explicit test-only environment variable and sentinel, refuse to overwrite the input DB, and never derive a normal app-data path. Passing actual filesystem ENOSPC and read-only remount tests qualify those OS/filesystem paths only. The fixture also requires a distinct mounted device, a 32–128-MiB capacity and a separate 128-MiB filler-write cap; it refuses an ordinary host directory. This tiny volume cannot meet the production 1-GiB free-space floor: test-only schema setup bypasses only that admission check; the production writer must still reject low space. A direct SQLite insert deliberately bypasses the app guard to demonstrate actual FULL/rollback; it is not represented as successful remote ingestion below the floor.
- **Native synthetic**: the separate `dev.hmrguez.gitjuke.storage-recovery` unsigned app exercises the real WebKit/Tauri startup recovery UI using only its disposable local namespace. It does not use the normal app DB, create remote fixtures or establish live GitHub compatibility.

The migration engine's broad matrix derives its loop bounds from `SCHEMA_VERSION`; it already covers fresh version 0 and every supported older version 1–13 through 14 in DELETE and WAL modes. The matrix has **294 actual SIGKILL boundaries** (before steps, after each applicable step, before/after commit) and **238 injected space-failure points**. The schema-12 accounting and schema-13 interrupted-planning tests add eight specific SIGKILL cases. Prior schema-12 matrix counts must not be relabeled as current evidence; use the new run's outcome. No on-disk protocol/schema change is introduced here.

Full-ceiling applicability must include both `full_ceiling` and `actual_ceiling` filters: the latter covers source/check staging transfer and retained Activity old-image charging, which the former alone omits. Successful functional completion is not a performance, worst-case cardinality, memory, temp-space or peak migration bound.

## Integration

New IPC commands: `startup_status` returns `{ready,databasePath,databaseState,message}`; `retry_startup` returns the same report after a serialized attempt. They are shell-level and remain available without Runtime. Ordinary commands still require Runtime and the reader mounts only after readiness. All tray/window/close callbacks that use Runtime must use `try_state` while storage startup is blocked. Independent notification/login/lifecycle handlers must follow the same rule and cannot start remote work or dispatch without a live validated runtime.

`StorageUsage` adds `transientBytes: number | null`; consumers must treat null as unknown, never zero, and must not call measured files a complete total.
