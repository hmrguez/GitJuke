## Decision and implementation

The prior `activity_due` statement applied due-time, pending-job and joined watch-reason eligibility before its final `ORDER BY due,repo,number LIMIT 128`. A long rejected target prefix, or many ineligible historical stable IDs sharing one repository/number, could therefore cause growing query work before the limit.

`activity_store.rs::activity_due` now delegates to `activity_due.rs`. Target reads take at most **128 native repository/number candidates** from the existing Activity-target primary-key index. First and successor statements are separate; the tuple seek supplies the lower bound directly. Due-time rejection and pending-job checks occur after the candidate limit. Pending membership uses the existing exact unique job key, preserving the original decimal-number concatenation and case-sensitive match, regardless of that job's own dispatch deadline.

Unfinished targets remain eligible without watch membership, as required for notification-derived hydration. Completed targets require at least one non-selected watch reason. Matching watch locators use the existing covering `(repo,number,id)` index in **128-ID windows before source filtering**. The ID successor prevents rejected aliases from becoming an unbounded joined prefix within one query. Each source probe is an indexed identity lookup: only the unique exact value `selected` can be rejected, so at most two reasons need examination. Exact-case `Selected` continues to differ from `selected`, matching the preceding SQL.

A max-heap retains at most **128 eligible `(due,repo,number)` tuples**. It replaces its worst tuple only with an earlier candidate. Once full, candidates that cannot improve that prefix skip eligibility probes. Sorting only this bounded heap returns the exact preceding SQL order, including due ties, native BINARY repository collation and signed numeric keys. Numeric conversion to the existing unsigned API occurs after ordering. The existing `time as i64` conversion and inclusive `due <= time` semantics remain unchanged.

This deliberately uses existing indexes instead of adding a due-order index or maintained membership relation. It introduces **no migration, persistent cursor, index, trigger, accounting state or scheduling reservation**. Schema remains **14**. Target and locator buffers and the heap each contain at most 128 metadata identities; no payload bodies are read. The number of windows/point statements still grows with stored targets and rejected aliases. Every call may revisit the same history. Total traversal time, variable key bytes and total allocator/temp usage are not bounded by these cardinality limits.

## Snapshot, visibility and mutation contracts

Standalone selection owns one SQLite read transaction covering all target windows, locator windows, pending-key and source checks. A caller already inside a transaction keeps its own snapshot and transaction ownership. Concurrent WAL changes cannot mix old target candidates with new pending or watch membership. Results are returned only after the complete traversal and successful read-transaction commit. A late read failure returns an error, releases an owned snapshot and discards the partial heap; it cannot return a partial eligible list or certify recovery.

Native main-table scans are blocked while any publication marker remains, including planning, applying and committed cleanup phases. Hydration scheduling cannot bypass old-snapshot reader overlays to observe a partially applied target/membership publication. Existing startup/repair completes publication before remote eligibility. Protected cached UI reading retains its existing views; this scheduling query does not replace those readers.

Selection performs **zero direct row mutations**, verified against SQLite `total_changes` and full input/history snapshots. It adds no bookkeeping to the **128-total-direct-mutation cap**, no presentation revision, target reset, queue reservation, progress/baseline/recovery completion or intent update. Existing queue insertion/descriptor bounds and generation/deadline/Pause checks remain responsible for dispatch after selection; this slice does not qualify the entire scheduling pass or durable queue SQL.

The inclusive **524,288,000-byte** shared disposable ceiling, retained old payload images, transactional accounting, exact LRU eviction order and atomic publication visibility remain unchanged. Activity/seen/dedup/progress/baseline/recovery history and terminal attempted/unavailable intent/member/attempt records, identity, persistent Pause, validators/server deadlines and permitted cached navigation remain protected.
