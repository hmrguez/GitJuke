## Behavior and interfaces

`alerts.rs` owns notification settings, permission observations, recovery reconstruction, reservation, final revalidation and attempt/click ledgers. Settings default disabled, generic and skippable. Only `enable_notifications` asks the native adapter for permission, after committing the explicit enabled choice. Reading settings, startup, background activation and category changes never request permission. Denial preserves monitoring and Activity, with an Open System Settings action. Repeated Enable in a denied state refreshes the actual OS status without requesting again. The separate opt-in metadata setting permits cached repo/PR title/actor, never source bodies/logs; every visibility class shares the same default. Unknown permission prevents dispatch.

Per-category activation timestamps and a committed intent-ID floor exclude existing backlog on enable/re-enable and OS grant transitions. Equal-second source times at the opt-in boundary are conservatively suppressed; source timestamps cannot prove which side of the UI click they occurred on. Local unseen state is untouched. Old unavailable/attempted histories are never reset. New intents are pending only while the locally observed permission is granted and alerts enabled; otherwise they are terminal unavailable. Small and journaled large-batch paths use the same captured intent state.

Existing completed hydration batches group per PR without a deliberate delay; post-recovery-boundary activity can use ordinary grouping while recovery is incomplete. Existing first-sync/manual/Pause/recovery classification remains authoritative. Restart/resume/wake moves only pending intents to recovery. Reconstruction streams 60 member IDs per transaction, with a durable per-intent keyset cursor and idempotent catch-up membership. It leaves unavailable/attempted intents terminal, then marks reconstructed source intents terminal. Existing recovery readiness still requires all discovery, enrollment, hydration and authored-check subcases; only its completed single cross-PR summary can dispatch. Seen/expired/category-disabled/denied/stale-head members are re-filtered before dispatch.

Reservations are in-memory and carry the account generation, serialized alert policy, exact eligible-ID digest, count and representative destination. Losing a reservation leaves an unattempted intent for ordinary recovery. The sole worker validates the bound GitHub identity through its existing serialized gh transport and core deadlines/budgets, then revalidates local permission, Pause, categories, seen, denial/Clear/publication/generation, and current head/current terminal retry identities. Local writers remain excluded through OS enqueue. A SQLite transaction commits the terminal attempted state, a unique attempt marker and representative source identity **before** invoking the platform. A failed marker commit cannot dispatch. Crash/error/unknown OS outcome after commit never retries; delivery is not a seen receipt. External account/OS state can still change after its last observation; no absolute race-free OS/GitHub claim is made.

`src-tauri/src/notifications.m` uses Apple's UserNotifications framework. `willPresent` explicitly requests banner/list presentation for foreground arrivals. The OS receives generic text by default and only `gitjuke-intent-<integer>` as the request identity; no repo, URL, source node, body or actor is embedded in click payloads. Default clicks return only the integer, bring the existing reader forward, and are resolved against attempted durable membership under the original validated account. Exact comment/review/mention destinations reuse Conversation's direct-node/segment receipts. Check/request outcomes reuse their existing explicit Activity destination; summaries or unavailable/expired/denied sources open Activity with an explicit unavailable label where applicable. Disposable payload eviction/Clear retains the exact source identity: comment/review/mention clicks can use the ordinary direct-node reader/refetch path, and metadata-only check/request destinations remain honest placeholders until a complete source is available. No arbitrary URL/command API is added. Pending clicks wait in the running application while identity is locked; OS cold-launch behavior remains a signed-native qualification gate.

Workflow outcomes require positive GitHub-supplied run and runAttempt identities plus a terminal suite. Jobs in the same workflow attempt coalesce; independent runs and explicit retry attempts remain separate. Before dispatch the same terminal identity must remain in the current complete check snapshot, excluding stale head/retry results. External suites retain their supplied stable suite/commit identity as **ineligible** Activity with an explicit retry-identity-unavailable reason. Legacy statuses also remain visible but are ineligible where no authoritative workflow/suite attempt exists. No timestamp, branch, job-name or missing-job inference fabricates a retry ordinal. Generic external retry delivery is not qualified or claimed: the GitHub suite schema supplies no general attempt ordinal.

Schema 15 adds only `(state,id)` dispatch/reconstruction indexing. It does not rewrite terminal rows or erase any source/seen/dedup state; older binaries reject the newer schema. Alert writes use the existing global 128-direct-mutation allowance and shared payload budget. Reconstruction windows hold at most 60 IDs; reservation membership windows hold at most 128 IDs and a digest/count/representative, without a materialized whole-intent ID list. Existing broad check classification and aggregate Activity reader query costs remain their previous open bounds; this slice does not claim whole-request constant time or qualify native maximum-memory/performance.
