## Audit and implementation

Retention previously combined up to 128 Activity candidates (each potentially deleting payload, catch-up progress and minimal Activity), 128 content rows, 128 check contexts plus completeness updates, and 128 rows of each metadata class, followed by revision. These were per-class limits, not a global transaction limit.

Each maintenance pass now performs one transaction with **at most 128 direct mutations total**. It reserves one mutation for revision, then spends the shared remaining allowance in deterministic class/key order. Activity reserves worst-case three mutations per identity and deletes its dependent payload/progress/minimal row atomically. Check expiry reserves worst-case two per context and invalidates completeness in the same transaction as deletion; already-normalized states consume no update. Remaining content, validators, API cache health and obsolete empty check state use only the allowance left. Server deadlines, payload ownership, staged/queued checks and watched current heads/merge commits retain their guards. Empty passes do not bump revision. A runtime total-changes guard rolls back an unexpectedly oversized transaction.

A maintenance pass can leave physical candidates for later passes. The existing 90-day Activity and 30-day payload/check filters remain authoritative on writable and protected cached readers. There is no new completed-cleanup claim or durable cursor: every committed prefix is a valid cache state, and persisted candidates are the restart worklist. Expiration never marks seen or removes seen/dedup, terminal attempted/unavailable intents, members or attempts. The audit found `activity_seen` could mark physically retained but logically expired loaded IDs; its existing 100-ID atomic snapshot update now requires the Activity lifetime predicate too.

The remaining runtime sweep writers were unbounded DELETEs of all reserved head descriptors after overflow, all per-PR abandoned Activity staging after hydration failure, and an UPDATE of all watched due timestamps during manual refresh. `control_sweep` persists one exact operation/scope before cleanup. Each transaction mutates at most 127 candidates and, when finished, deletes the marker in the same transaction. Marker admission is a separate one-row commit. No payload admission is needed: these operations add no disposable bodies and never change published payloads/membership. Earlier committed disposable queue/staging/due cleanup may survive a later failure. Publication transactions and their old/new visibility remain unchanged.

Startup resumes publication, existing purge/clear/invalidation work and then control sweeps before abandonment cleanup or remote scheduling. Current-session repair resumes them before retention and the committed health/checkpoint probe. Pending sweeps block explicit remote eligibility and recovery completion. A failed head-reservation sweep also clears stale in-memory head descriptors after successful repair. SQL/free-space errors follow existing storage protection and cached-reader paths. Persistent Pause, bound identity, server validators/deadlines, baseline/recovery history and terminal eligibility remain intact.

Already-bounded startup cleanup, enrollment, recovery initialization and source/watch/check/Activity publication were retained. Activity first-page reset still uses its existing bounded helper; only the demonstrated unbounded error-path reset was changed. The existing 100-ID seen update costs at most 101 mutations including revision. Point mutations, 50-thread notification completion and small/journal publisher guards remain separately bounded. Migration itself remains one atomic upgrade and is intentionally not split into partial schema commits.

## Schema and shared storage

Schema **11** adds `control_sweep(id,kind,args)` and a compatibility barrier so schema-10 binaries cannot ignore pending work. Schemas 0–10 upgrade through the existing synchronized, space-checked atomic migration. Historical downgrade fixtures remove the newly introduced table when constructing old schemas; no migration assertion is weakened.

The inclusive shared disposable ceiling stays **524,288,000 bytes**, including staging and retained publication old images. No payload writer, byte accounting or admission policy is changed. Managed metadata/journal overhead remains separately measured; no whole-database limit, file shrink or VACUUM is promised.
