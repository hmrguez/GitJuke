## Audit and scope

A row mutation limit does not bound the candidates SQLite must examine. The previous retention predicates could scan long protected prefixes to find a victim, combine expired/orphan content with an OR, sort published checks by a joined timestamp, or sort tied Activity occurrence times before applying LIMIT. Publication application selected twelve unapplied rows by scanning the journal's growing applied prefix.

This slice bounds **candidate cardinality and sort/materialization work for retention selection and publication application**, with deterministic operation counters and restartable progress. It does not claim every SQLite query, total operation duration, metadata byte length or physical temporary allocation is bounded. The inventory below records the remaining work rather than extending the new qualification to unrelated paths.

## Implementation and durable progress

`retention_window.rs` handles five classes. It captures an indexed maximum key as a fixed upper fence, then uses an indexed native tuple seek to select at most **128 identities before ownership, deadline or current-state eligibility predicates run**. A materialized CTE contains only one or three key columns, never fetched content/check bodies. Exact ownership, deadline, pending-traversal and watched-head/merge probes evaluate only those candidates. Published-context selection uses a partial `(pr_id,commit_sha,id) WHERE staged=0` index. Empty-check selection uses `(accessed,pr_id,commit_sha)`, with the expiry range applied at the index.

Each maintenance pass advances at most one nonempty window per class. At a completed fence it may first execute an empty seek, then acquire a new one-row maximum and start the next cycle; it still examines at most 128 eligibility candidates in that class. Fixed fences prevent newly appended higher keys from keeping the cursor chasing the tail. Changed deadlines/ages and new keys behind the frontier are revisited on the next cycle. Neither a missing nor a stored cursor certifies completed cleanup, successful source progress, a baseline or recovery readiness. Cursors are disposable incremental work.

The selected keys are ordered in Rust using native integer/text tuple comparison over at most 128 metadata records. This avoids relying on an unspecified outer materialized-CTE scan order. SQLite performs no candidate sort or automatic index in the qualified plans. Materialization is bounded in **rows**, not universally in bytes: key/URL lengths, B-tree height, overflow pages, SQLite caches/allocator behavior and physical temporary-file allocation still require separate qualification. Zero SORT counters do not mean zero ephemeral SQLite storage.

`retention_cursor(class,position,ceiling)` commits with the dependent deletions that justified its advancement. One mutation slot is reserved for cursor bookkeeping before deleting an eligible unit, and the maintenance transaction still reserves presentation revision. Every transaction remains **at most 128 direct mutations including cursor/revision bookkeeping**. Cursor-only progress does not change presentation revision. Activity payload/catch-up/minimal deletion and published check invalidation/deletion remain indivisible. A failed checkpoint rolls back the complete current maintenance batch; prior committed windows survive.

Read-time 90-day Activity and 30-day content/check expiration remains authoritative while physical cleanup waits. Future server deadlines, current watched head/merge health, pending/staged contexts and payload ownership retain their guards. Expiration does not mark seen. Stable identity, Pause, validators/deadlines still in force, baseline/recovery boundaries, seen/dedup and terminal attempted/unavailable intent/member/attempt history survive. A retention cursor neither hides valid content nor delays otherwise-ready recovery. Existing failure protection, cached opening, startup/repair and paused periodic maintenance apply to cursor failures; no new remote eligibility is granted by cursor advancement.

Publication's partial `publication_row(seq) WHERE applied=0` index changes selection only. Preparation, old-snapshot protection, all admission/revision/direct-mutation limits, the visibility commit and bounded reclamation are unchanged. The inclusive shared disposable ceiling remains **524,288,000 bytes**, including staged bodies and retained old images. Cursor/index metadata is managed-file overhead, not an exemption for payloads or a whole-database limit.

## Schema compatibility

Schema **12** adds the cursor table and four indexes: Activity occurrence/key expiry, check access/key expiry, published-context keys and unapplied publication rows. Older schema-11 binaries must reject schema 12 rather than ignore cursor bookkeeping or depend on older selection plans. Schemas 0–11 upgrade in the existing synchronized, admitted, single atomic migration. Historical schema reconstruction removes the new table/indexes before emulating older databases. Atomic migration matrix results are recorded below; native migration, peak allocation, large old-schema index-build sorting and physical faults remain Pending.
