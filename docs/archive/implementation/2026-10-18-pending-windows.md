## Selection and fairness

`watch_store.rs::pending` previously filtered deadline/resource/Pause eligibility and sorted by foreground priority before a final 128 limit. A separate oldest-background query could traverse the rejected prefix again. Those limits bounded output, not candidate work or sorting. `pending_selection.rs` now implements the same selection through native candidate windows:

- Read at most **128 `(seq,at,resource,manual,foreground)` metadata rows**, ordered by the existing integer primary key. Separate first/successor statements avoid an OR around the lower bound; signed sequence endpoints need no arithmetic sentinel. Deadline, resource and Pause rejection happen after this limit. Rejected keys and job bodies are not loaded.
- Retain at most **128 priority/sequence ranks** in a max-heap. `(Reverse(foreground),seq)` matches the previous `foreground DESC,seq` order without negating a signed priority. Raw integer priority is retained until the final API boolean conversion. Track the first eligible `foreground=0` sequence separately as the oldest eligible background job.
- If the selected page is full and all entries convert to foreground true, replace its last priority-ranked job with that background job when one exists. This preserves the exact previous reservation, including 126/127/128/140-foreground boundaries, multiple background jobs and rejected earlier backgrounds.
- Sort only the bounded selected sequence set in ascending order, matching the previous returned order. Read each selected full descriptor by exact primary key, at most **128 point reads / 128 returned descriptors**. Job body decoding never occurs during the rejected-prefix traversal.

The existing global core-budget gate remains authoritative, including when other resources are eligible. Resource budgets/backoff and inclusive job deadlines retain their boundaries. Paused selection requires exactly `manual=1`, as before. Invalid optional search/GraphQL budget decoding remains ineligible, while a core-budget error propagates; no error-policy revision is introduced. The old SQL interpolated an unsigned time literal, so timestamps above `i64::MAX` admitted all signed SQLite job deadlines. Comparing the signed stored deadline and unsigned caller time in `i128` preserves that behavior; casting the time to `i64` here would change it.

The runtime queue still coalesces descriptors, holds at most 128 materialized jobs and services the oldest eligible background job after at most three foreground dispatches. A new direct selector-to-runtime-queue test verifies exact selected tickets **1…127,141** and pop tickets **1,2,3,141,4**, with all 142 durable pending records still present until acknowledgement. Selection itself does not acknowledge, reserve, rotate, reschedule or change any intent. Existing retry, coalescing, acknowledgement and startup manual-job reset semantics remain unchanged.

## Snapshot, visibility and storage contracts

Standalone selection owns one read transaction covering publication readiness, budget/backoff reads, Pause, every candidate window, background reservation and final key/job/flag point reads. An existing caller transaction retains its own snapshot and ownership. Concurrent WAL writers cannot combine an old metadata prefix with new policy, background eligibility, flags or job bodies. Results are returned only after complete traversal, successful descriptor decoding and owned read-transaction commit. Late failures discard the provisional heap or partially assembled descriptor vector and release an owned snapshot; no partial queue is returned.

Native main-table scans are blocked while any publication marker remains, including planning, applying and committed cleanup. Prepared pending old/new images retain their protected reader visibility. Startup/repair must complete publication before scheduling from canonical queue state. Cached UI reading and compatible read-only opening retain their existing behavior; selection does not bypass old-snapshot overlays to dispatch partially applied state.

Selection performs **zero direct row mutations**, checked by actual `total_changes` and exact pending/input/accounting/history snapshots. There are **no new cursors, tables, indexes, triggers, accounting writes or migration steps**; schema remains **14**. The **128-total-direct-mutation cap**, including dependent bookkeeping, remains unchanged. Presentation revision, generation, deadlines, durable Activity/seen/dedup/progress/baseline/recovery state and terminal attempted/unavailable intent/member/attempt records remain intact.

The inclusive **524,288,000-byte** shared disposable ceiling, retained old payload images, maintained accounting, exact LRU order, identity, persistent Pause and cached navigation remain protected. A killed read cannot create an acknowledgement, durable selection prefix, completion claim or OS attempt. Normal startup still clears session-only manual/foreground flags before dispatch; tests distinguish that intentional startup normalization from changes by selection.

Each metadata buffer, rank heap, selected-ID set and returned descriptor collection is bounded by **128 entries**; the background candidate is one sequence. These are cardinality bounds. Resource/key/body/JSON lengths, whole settings/budget/job parsing, total allocator/cache/temp bytes and B-tree/key comparison costs remain open. Every call can traverse the entire pending table, and later calls can repeat that traversal. No constant/sublinear total selection time or complete scheduling-pass bound is claimed. `due_watches`, reserved-head JSON expansion, later runtime job-eligibility filtering, reader queries and control/startup/recovery/purge sweeps remain separate work.
