## Audit and implementation sequence

The previous admission slice bounded eviction but left the publisher's own writes unbounded. Source membership replacement, global legacy-watch flag repair, team removal, head-change invalidation of historical check states and complete check-snapshot replacement could each mutate arbitrarily many rows. Merely committing smaller parts would expose mixed membership, old/new heads, partial checks or premature successful progress.

The implementation sequence was: build a durable publication journal and protected old-snapshot reads; replace the source/watch/check writers; combine publication and admission under one transaction allowance; integrate restart, storage protection, repair and lifecycle; add mutation/fault/process-kill/full-ceiling qualification; retain a single-transaction path for provably small updates; update acceptance evidence.

The covered operations are PR-source page staging and completed membership publication; team page initialization/staging and completed team publication/removal of obsolete team memberships/descriptors; remembered selection and selected-only membership/flags; selected-PR registration; watched-head/closure publication, staged-check reset and historical check-state invalidation; check first-page/overlap staging and complete snapshot publication. Source first-page reset retains its already-qualified bounded implementation. Activity's own publication/initialization and recovery-summary mutation bounds remain separate work.

## Transaction and visibility model

Every covered publication transaction has a **global maximum of 128 direct row mutations**, including its own writes, revision and admission's expiration/content/check deletion and completeness invalidation. The shared admission helper reserves only the allowance left after the publisher's writes. If more space is needed, the candidate rolls back before the existing independently bounded LRU reclamation and retry. No publication is committed merely to make space.

`publication_small.rs` first proves a conservative small-operation bound using capped counts and identity lists under the runtime's existing serialization. It then executes the whole operation in one SQLite transaction, with targeted watch-flag updates rather than a global UPDATE. If it cannot prove that bound, it uses the journal. These thresholds choose an implementation path; they do not cap watches, source membership or traversal size. A failed small transaction preserves the previous publication in the usual SQLite manner, apart from previously committed independent disposable reclamation.

Proven-small selection/team metadata changes use a counted transaction with the same 128-mutation guard and storage check, without payload admission: they add no disposable bytes. This preserves cached selection's behavior rather than expiring unrelated content before hydration. Payload writers continue to share their remaining allowance with admission.

Head reservation now builds the pending head-ID set once per query instead of reparsing every pending batch for each watch. The predicate preserves reservation exclusion, due eligibility and selected priority, and filters null/non-text descriptor IDs. A dedicated store regression checks exact reserved IDs, unrelated jobs, null descriptors and eligibility after acknowledgment. This fixes one demonstrated scheduling bottleneck; it does not establish general SQLite query/cardinality/temp/time bounds.

For larger operations, `publication.rs` uses the schema-9 `publication` and `publication_row` tables:

1. Commit the operation identity and its bounded fetched input. An exact SHA-256 request identity survives consumed input, allowing a retry to finish the pending operation without publishing an empty source/team set or advancing a head epoch twice.
2. Prepare fixed-size batches of prospective changes and old images. Each batch holds at most twelve row identities/values in Rust. Unchanged metadata is excluded. Payload destinations reference their input/staging instead of embedding another payload in the change plan.
3. Apply bounded batches, retaining old published row images. Each target change and its applied bit commit together. Inputs are moved: consumed source/check staging is removed in the same transaction; forwarded page payloads are replaced by null at their original input paths, preserving remaining references without keeping a second input copy.
4. Commit the visibility change and presentation revision together. This is two mutations, or three for a complete check publication's final actual-count/completeness check. Complete checks are never inferred from missing/evicted contexts.
5. Reclaim journal rows in transactions of at most 127 deletions plus the final marker deletion. A committed marker never reapplies changes or increments the revision again.

Preparation/application use the admission helper's remaining transaction allowance; metadata phase changes and finalization are fixed small transactions. First-page/overlap reclamation of unpublished staging uses at most 128 deletions per transaction and never changes published membership, Activity or successful progress. SQLite query execution, sorting, temporary storage, bytes written and total synchronous duration are not bounded by these row limits.

The runtime continues to serialize the operation. Successful execution exposes only the complete result. If a later batch fails, `Store` installs connection-local protected views over old row images; the same views are installed by `open_cached` after an interrupted startup. Before the visibility commit, these return the previous published membership, locators/heads, list bodies, check snapshot/health, selection and team state. After the commit they return the complete new canonical state, even if journal reclamation is unfinished. Raw `main.*` inspection may see physical partial application; it is not an application reader surface. The protected views are removed only under serialization before repair continues the physical operation.

Any failure after durable journal creation stops remote eligibility. Startup and current-session repair finish publication before other cleanup, retention, recovery/probing or remote scheduling. Recovery completion and terminal-check classification reject pending publication. A reader close received while repair is blocked is reapplied to selected-only membership before scheduling resumes, preventing stale selected-only reasons from surviving repair. Stale/mismatched head identities and locators are rejected before a new publication.

## Payload budget and preservation

The ceiling remains **524,288,000 bytes, inclusive**. New unpublished input payloads and **every retained old payload image** are included as non-evictable staging alongside existing disposable classes. Canonical disposable copies remain eligible for LRU eviction; protected reads can retain the charged old image. Plan rows hold references rather than additional new-body copies. Moving a payload clears its original staging/input location transactionally. Metadata and SQLite record/JSON/journal overhead remain part of measured managed files, rather than a whole-database payload-size promise.

Byte accounting uses the bundled SQLite's `octet_length` for stored columns, preserving byte rather than character counting while avoiding loading overflow payload pages just to count them. Old-image byte lengths are recorded during preparation, so accounting does not repeatedly decode every retained body. The bundled amalgamation explicitly implements this function with column byte-length flags to avoid unnecessary data loading; this is a local dependency-source verification, not a system-SQLite assumption. Full query/cardinality/time/temp qualification remains Pending.

Watch identities/reasons outside the completed reconciliation, minimal Activity/unseen/seen/dedup/progress/baseline/recovery boundary, settings/Pause, bound identity, terminal attempted/unavailable intents and membership/attempt history, and notification validators/server deadlines survive publication and faults. No delivery backlog or native dispatch is introduced. Epochs are assigned once at head acceptance and replayed as fixed values; exact retry and interrupted application cannot increment them twice. Discovery and check completeness still require successful complete enumeration, with source/head/generation guards preserved.

## Schema and restart compatibility

Schema **9** adds the two journal tables, including retained-payload byte accounting. Schema 8 binaries must reject this database rather than ignore unfinished publication. Supported schemas 0–8 upgrade in the existing single fully synchronized atomic migration, with space admission at every step and commit. Historical reconstruction fixtures remove the new tables. Migration qualification expands to **144 actual SIGKILL cases and 108 injected space failures**, across schemas 0–8 in DELETE/WAL modes.

Protected cached startup still requires an intact current-schema database. No downgrade/reset, VACUUM, file-shrink, sufficient peak-allocation guarantee or signed/native migration claim is added. Actual native schema-9 migration and signed compatible/incompatible binary replacement remain Pending.
