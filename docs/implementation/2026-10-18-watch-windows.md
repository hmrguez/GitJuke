## Audit and implementation

The preceding `due_watches` query filtered all watches, expanded pending `Heads` jobs into a reserved-ID relation and sorted selected priority/due/ID before its result limit. Its output limit did not bound rejected watch prefixes, pending-job traversal or expanded reservation-set size.

`watch_store.rs::due_watches` now delegates to `watch_scheduling.rs`. Native watch-ID windows contain at most **128 metadata candidates before filtering**; first and successor statements are separate indexed seeks. Inclusive due time, manual-refresh boundary and caller-selected priority use the previous signed SQLite conversions and exact comparisons. Membership and case-insensitive per-resource denial use indexed existence/point lookups after the candidate limit. Any watch reason still establishes membership, including selected-only reasons; multiple reasons never duplicate a target.

A rank heap retains the best caller-requested prefix in the exact prior order: **selected repository/number first, due ascending, native stable ID ascending**. The previous `None` fallback to empty repository/number zero is preserved. Heap comparisons use native UTF-8/BINARY text order; unsigned number/generation API conversions happen after ordering. Uncompetitive candidates can skip membership/reservation checks. Heap capacity grows only as accepted candidates are found; a large requested limit does not cause an up-front allocation.

The existing public `limit` remains caller-defined. Heap/output cardinality is at most that requested limit, not a new hard 128-watch cap; a 129-target result is explicitly tested. Production head batches start at **10** and may shrink after oversized responses. Watch candidate buffers and reservation membership remain capped at 128 independently of that request. No watch membership is dropped or age-capped to satisfy these query bounds.

## Bounded reservation membership

For each nonempty watch-candidate window, a membership map holds at most **128 candidate ID → reserved flags**. Pending sequences are read in indexed windows of at most **128**, including non-head jobs and arbitrary rejected prefixes. Each job's canonical `Heads` JSON is projected by an exact sequence read using SQLite `json(job -> '$.Heads')`; only one projection is held at a time. Pending dispatch deadlines, resources, manual and foreground flags do not filter reservations, matching the preceding query.

`watch_reservations.rs` walks the projected array or object through borrowed `RawValue` entries, one at a time, without building a whole reserved-ID set or collecting the array. A scalar projection is one entry. SQLite evaluates `json_type(value,'$.id')` / `json_extract(value,'$.id')` through a `json_each` wrapper containing **exactly one entry**, so filtering never traverses a growing SQL relation. Only text identities set candidate flags. Canonical projection preserves SQLite path, JSON5 and duplicate-root-key semantics; the one-entry SQLite evaluation preserves the old decoded-value behavior for object entries, nested JSON text strings, null/nontext IDs and malformed-text failures. Case, UTF-8, empty and embedded-NUL identities remain exact. Duplicate reservations consume no additional membership state.

SQLite still parses/canonicalizes the variable-length stored job/path, and Rust/SQLite still parse variable-length individual entries. Those whole-value/variable-byte operations remain **Pending**; bounded SQL candidate counts and VM counters are not a per-statement CPU or total JSON-memory guarantee. A watch window can require reading every pending job and every head entry, and later watch windows can repeat that work. Cumulative traversal and repeated parsing remain open. The removed global SQL expansion/materialized ID relation is the specifically closed candidate/cardinality gap.

## Snapshot, failure and storage contracts

One read snapshot covers the manual boundary, every watch/pending window, membership/denial probe, projection, streamed entry and generation returned to the caller. A standalone call owns its read transaction; a caller already in a transaction retains its snapshot/ownership. A concurrent WAL writer cannot mix old watches with new membership, denials, boundary or reservations. Results are returned only after complete traversal and successful owned read commit.

A pending publication marker blocks native main-table scheduling in planning, applying and committed cleanup phases, while cached readers retain their old/new protected views. Startup/repair still completes publication before scheduling resumes. A late watch, pending-window, projection or entry failure returns an error and discards all provisional selection/flags. Malformed stored reservations fail closed, preserve their original bytes and cannot become successful empty reservations or completion claims.

Selection performs **zero direct row mutations**, verified against SQLite `total_changes` and exact input/accounting/history snapshots. It adds no reservation writes, persistent cursor, index, trigger, accounting state or migration; schema stays **14**. Existing enqueue, retry/acknowledgement and publication/maintenance writers keep the **128-total-direct-mutation cap** including bookkeeping. Selection does not alter due/success, epochs, source membership, queue history, progress or presentation revision. Repeated scheduler calls reserve disjoint batches through the existing durable enqueue; successful refresh deadlines continue to rotate otherwise eligible watches. Foreground/background queue fairness remains the preceding implementation's contract.

The inclusive **524,288,000-byte** shared disposable ceiling, retained old payload images, transactional accounting, exact LRU order, atomic visibility, identity, persistent Pause, validators/server deadlines and cached navigation remain unchanged. Durable Activity/seen/dedup/progress/baseline/recovery state and terminal attempted/unavailable intent/member/attempt records remain protected.
