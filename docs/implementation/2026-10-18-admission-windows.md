# Shared admission byte-total and LRU query windows — 2026-10-18

Status: implementation complete; scoped final verification recorded below. Development **0.1.0**, SQLite schema **12**, unchanged. No applicable AGENTS.md or Git repository is present. Settled contracts and release limits are unchanged.

## Scope and implementation

Shared admission previously ran full-set SQLite SUMs for canonical/staged bodies and retained old images, sometimes repeatedly in one candidate transaction. Its limited victim query sorted a union of ordinary content and every published check context joined to snapshot state. LIMIT capped returned victims and mutations, but did not cap aggregate inputs or sort cardinality.

`admission_query.rs` replaces these statements with **at most 128 candidate rows per SQL window**:

- Canonical content, the three staging tables, check contexts and publication rows use native rowid seeks. Each window visits at most 128 rows **before** deciding whether a journal image is chargeable or a context is staged. Lengths and protection flags are accumulated in Rust. The first seek includes `i64::MIN`, later seeks are strict, and `i64::MAX` terminates without arithmetic overflow. Rowids are ephemeral scan positions, never durable identity.
- Ordinary content uses the existing `(accessed,key)` LRU index and selects at most the remaining mutation allowance's number of identities/lengths. Expiry remains a direct timestamp range.
- Published checks use the existing partial `(pr_id,commit_sha,id) WHERE staged=0` index. A materialized window contains at most 128 contexts before exact snapshot-state point joins. Missing state means timestamp zero, as before. The next seek uses the window's maximum native key, independent of unspecified materialized-output order. Empty states and staged contexts cannot cause an unbounded rejected prefix inside a statement.
- A Rust max-heap retains at most 128 global victims across these windows. A window/vector can hold another 128 metadata records. The exact order remains `(accessed, class, key/PR, commit, context)`, with ordinary content first on a timestamp tie. Only the selected metadata prefix is sorted in Rust; no payload bodies are selected for LRU sorting.
- Publication input charging reads its singleton request and streams the applicable PR/context values with serde's borrowed `RawValue`. UTF-8 JSON substring lengths match SQLite's previous object-value charge, including escaped strings inside objects. It does not construct an array of all input values. Other request fields are skipped. The existing durable request text and individual body/key lengths are **not** given a new byte bound.

Admission computes one exact total/protected total in its candidate transaction, then subtracts exact canonical victim lengths as they are deleted. Retained old images remain charged independently; deletion never credits their bytes. This removes repeated total traversals in the same candidate. Storage usage reporting also uses these reads; when called outside a transaction, byte accounting owns one read transaction across all windows. A concurrent WAL commit cannot mix old canonical bytes with new staging/journal bytes. An existing caller transaction supplies the snapshot otherwise.

**This is a per-statement cardinality and sort bound, not constant-time admission.** Byte totals still traverse all six canonical/journal tables, and check LRU selection still traverses all published contexts. More rows mean more bounded windows, and a multi-batch publication repeats those traversals. Maintained constant-time totals, sublinear check-LRU selection, bounded cumulative duration and native responsiveness remain **Pending**. Variable body/request/key lengths, JSON parsing, B-tree height, allocator/cache behavior and physical temporary allocation also remain unqualified. Zero SORT/AUTOINDEX counters do not imply zero ephemeral storage or a universal VM-instruction bound.

## Atomicity, restart and compatibility

No schema migration, persisted counter, maintenance cursor or new write is introduced. The existing schema-12 indexes supply the seeks. A failed/interrupted read discards its ephemeral positions; retry recomputes from the current committed snapshot. There is no partial byte total that startup, repair or remote eligibility can mistake for durable completion. Invalid stored request parsing returns a storage-protection error, with candidate writes/revision rolled back and the original request preserved; a failed reporting read also releases its transaction.

The production inclusive shared disposable ceiling remains **524,288,000 bytes**, including all staging/request inputs and retained old payload images. The non-evictable charge is checked before reclamation. Zero-byte victims still precede later victims. Check invalidation, protected old-check completeness updates and payload deletion remain atomic under the existing shared **128-direct-mutation** allowance including revision/bookkeeping. Large reclamation still rolls back the complete candidate before independently committed batches. Small operations still commit once; journal preparation/application, old-snapshot readers, one visibility commit, exact retries and startup/repair readiness barriers are unchanged.

No history is admitted as a disposable victim: identity/Pause, seen/dedup, progress/baseline/recovery, terminal attempted/unavailable intent, membership and attempt records retain their contracts. Logical expiration, denied/cleared content barriers, cached navigation, validators and server deadlines are unchanged. No new successful-recovery claim or remote eligibility follows from completing a query window.
