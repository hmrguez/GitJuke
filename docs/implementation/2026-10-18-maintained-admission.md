# Maintained shared accounting and indexed LRU — 2026-10-18

Status: **Pass, scoped implementation and verification**. Development **0.1.0**, SQLite schema **13**. A Git repository is present; no applicable AGENTS.md was found in the workspace or its ancestors. Settled product contracts and release limits are unchanged.

## Audit and decision

The [preceding admission windows](2026-10-18-admission-windows.md) bounded individual statements but still traversed every payload/journal row and every published check context during admission. Repeated admission therefore repeated cardinality-dependent work.

Three options were considered. Retaining scan windows cannot close that gap. A Rust transaction accumulator would require every write, rollback, savepoint and connection seam to cooperate; deferring its flush would also create an additional commit-time mutation requiring reservation everywhere. Copying snapshot access times into every check context would make one cached check access fan out over arbitrarily many contexts. This slice instead uses SQLite-maintained byte totals and one indexed frontier per **nonempty published check snapshot**. Trigger writes are explicitly charged to the same transaction allowance as their initiating writes.

`shared_storage.sql` installs the schema and triggers. `shared_storage.rs` registers the request-charge function, enables recursive delete triggers for REPLACE semantics, supplies conservative cleanup costs and enforces the shared 128-mutation guard. Connection initialization happens before migration/startup work and on compatible read-only cached connections. The new schema prevents older binaries from ignoring this accounting contract.

## Maintained accounting

`main.shared_bytes` has one row containing total bytes, non-evictable bytes and an invalid-request count. Admission and storage reporting read that singleton in the caller's transaction; standalone reporting owns a read transaction. No runtime payload-table SUM, row-window traversal or request-array parse is needed to obtain usage.

Charges preserve the previous implementation exactly:

- Canonical content and every check context contribute their UTF-8 body bytes. Staged check contexts and the three staging tables contribute protected bytes as well.
- Retained content images and retained **published** check-context images contribute their recorded `old_bytes` independently of canonical bodies. Old staged images are not charged a second time. Canonical eviction cannot credit the retained image; journal cleanup releases its separate charge.
- Source-page/check request arrays and selected/head PR inputs use the existing borrowed `RawValue` parser. The deterministic SQLite function computes their charge when the request is inserted, changed or removed and during initial migration. Escapes, UTF-8, whitespace within object substrings and null array elements preserve the prior charge. Request consumption and its counter delta commit with the body application. This does **not** bound request parsing, `json_set`, serialization or variable request/body/key bytes; changing a large request can still repeat work over that request.
- Charge-changing writes update the singleton once. Equal-charge replacement, access-time-only updates and zero-byte bodies require no counter mutation. SQL integer/nonnegative/protected-within-total constraints fail closed. Malformed persisted request input increments an invalid flag rather than becoming a usable zero-byte total; reporting/admission return storage protection and candidate writes roll back. Original malformed input is retained.

There is no deferred accounting cursor, asynchronous recount, best-effort repair or startup “ready” marker. Payload, staging, request, retained-image and counter writes share SQLite's commit/rollback boundary.

## Exact shared LRU selection

`shared_check_lru` contains `(pr_id, commit_sha, accessed, first_id)` only for snapshots containing published contexts. Its `(accessed,pr_id,commit_sha)` index supplies at most the first **k** snapshots, where **k ≤ 128**. A min-heap merges their first contexts and advances only the contributing snapshot through an indexed published-context successor seek, at most **k** times. The content index supplies its first **k** candidates. A bounded max-heap retains the exact shared prefix.

The complete order is unchanged: **access timestamp, ordinary content before checks on ties, native content key or PR/commit/context keys**. Missing check state means timestamp **zero**. Inserting, moving, updating or deleting state updates at most the affected snapshot frontiers, without timestamp fan-out to contexts. Context insertion/removal/staging transitions maintain the first published key; deleting the last published context removes the frontier. Staged-only and empty snapshots never form a rejected selection prefix. Frontier existence/successor queries explicitly use the partial published-key index, including when a large staged prefix remains.

A selection uses at most **130 statements**: content, snapshot seeds and 128 successors. Each heap holds at most 128 identities; returned/window vectors are similarly capped. This is sublinear indexed selection in stored cardinality, with B-tree seek and key-comparison costs; it is not a constant-duration or variable-byte memory guarantee. There is no global SQLite victim sort. Zero-byte victims still consume their place in the prefix, and an insufficient mutation allowance stops before the next victim rather than skipping it for a cheaper later victim.

## Mutation budgets and publication

Every covered transaction remains capped at **128 total direct mutations**, including trigger writes, dependent state/old-image invalidation, cursors, revision and final markers. The common charge-changing content/staging write costs two mutations. A published-context insertion/deletion costs at most three; moving a context between snapshots can additionally touch both frontiers. Snapshot access changes touch one frontier rather than all contexts. A check admission unit reserves its payload cost plus each required live/shadow completeness update.

Cleanup loops select conservatively using worst-case row costs, measure actual `total_changes` including triggers, retain unfinished markers when the next unit cannot fit and enforce the transaction guard. Retention reserves four mutations per dependent Activity unit, two per content deletion and the appropriate check/cursor costs. Source/staging/startup/recovery/denial/clear/invalidation/control sweeps and journal cleanup all reserve bookkeeping. Journal cleanup takes at most 63 rows while allowing request removal. Activity staging takes 64 inputs per transaction; direct Activity publication takes at most 15 records. Source-page/check small-path preflight limits are reduced as necessary. Existing twelve-row journal application remains within the shared allowance.

Small publication remains atomic; larger publication still prepares durable old images, applies bounded batches, switches visibility once and cleans up afterward. Independent LRU reclamation may survive a later candidate failure, as before. Because bookkeeping now consumes allowance, exact committed disposable prefixes and revision counts can differ from schema 12. Tests retain exact prefix assertions with the new costs and keep the 128 guard intact.

The inclusive shared disposable ceiling remains **524,288,000 bytes**. Durable Activity/seen/dedup/progress/baseline/recovery history and terminal attempted/unavailable intent, membership and attempt records are not victims. Identity, persistent Pause, validators/server deadlines, denial/clear barriers and permitted cached navigation retain their contracts. Completing accounting or cleanup cannot certify recovery or unlock remote eligibility prematurely.

## Migration, restart and failure evidence

Schema 12→13 builds counters and frontiers in the existing single **FULL-synchronous** migration transaction, with space checks before the step and commit. A failed step or late space check publishes neither partial counters nor a partial index. Startup/repair still resume pending publication and maintenance before abandoning transient work or enabling remote scheduling. Cached reads use the existing old-image overlays and visibility barriers; reporting charges physical canonical/staged/retained images rather than the overlaid reader view.
