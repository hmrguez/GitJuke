# Choose large-diff reading and performance limits

## Question

Within the confirmed runtime transport/cache/IPC bounds and Stacks reader design, what can v1 render locally for large PRs, individual patches, long lines and inline threads, and when must it show an explicit limited state with an exact GitHub destination?

Set per-file and aggregate render/memory limits, lazy loading and virtualization behavior, handling of binary/generated/missing/oversized patches and incomplete file listings, revision-correct thread anchors, cancellation when selecting another file/head, and measurable responsiveness/accessibility acceptance fixtures. Distinguish upstream incomplete data, transport overflow and a deliberate local rendering limit. Do not imply that all files or lines are available when only a subset was read. Decide whether any explicit load-more override is supported and how it stays bounded.

### Reading policy and limits — proposals only, 2026-10-17

Open branches: reading format/loading granularity; default and exceptional local patch limits; honest source/local-limit states and revision-correct discussions; then the dependent rendering/accessibility and measurable performance acceptance round. The numbers below are proposed product limits, not measured performance or GitHub capabilities.

1. **Reading format and loading.** Unified diff only in v1. Keep the file navigator available and load/render the selected file, with no whole-PR patch prefetch. Underlying gh responses may include patches for other files; this policy limits requested work and frontend delivery, not a claim that the endpoint transfers only one patch. File metadata is paginated and navigation remains usable while discovery is partial. Restore file/scroll positions within the same revision. On selection change cancel obsolete selected-only work where safe, drop queued unnecessary hydration, and never let late responses replace the selected file. Already-completed results can enter their matching backend cache under the confirmed generation rules. On head change, show an update affordance and label any retained view with its old revision; explicit movement to the new revision resets/re-resolves anchors rather than mapping old line numbers blindly. Generated files are initially collapsed only when explicitly identified by reliable source metadata; otherwise treat them as ordinary files. Do not promise a generated-file classifier.

2. **Bounded local patch reading.** Automatically display an available complete patch up to 512 KiB of UTF-8 patch text and 5,000 displayed patch rows, counting context, additions, deletions and hunk/header rows. Both limits apply, inclusive. Above either limit offer an explicit Load large diff action only if the full patch is at most 2 MiB and 20,000 rows; that action does not override transport/IPC/cache/server limits. Beyond either hard limit show metadata and Open file in GitHub, without parsing/rendering a silently clipped prefix. A logical line exceeding 16 KiB UTF-8 also requires the limited state/GitHub fallback rather than unbounded horizontal layout. Preserve original whitespace and horizontal scrolling for supported lines; do not wrap code by default. Distinguish unknown size from zero; when metadata cannot establish eligibility, bounded backend acquisition/validation may be needed before choosing a render state. Never parse truncated transport output to estimate a patch.

   Keep one active rendered patch; retain at most 8 MiB of source patch text and 50,000 patch rows across active/recent frontend patch models, evicting inactive models first. These are source-data ceilings, not a total JS/DOM/process-memory guarantee; object/decoded-string overhead needs separate measurement in the next round. The backend remains under its confirmed 500 MiB shared disposable budget. Multiple sub-1-MiB IPC chunks may transfer an eligible large file; never weaken the confirmed per-response ceiling. No user override above the hard patch/line limits in v1. Syntax highlighting may be omitted for the explicitly loaded large tier; exact render strategy and measured performance follow after human agreement on these tiers.

3. **Partial/unavailable content and discussions.** Distinguish Not loaded, Loading, Complete patch for this file/revision, Source incomplete or patch missing, Local display limit, Transport failure/overflow, Binary, and Access unavailable. Never infer binary or generated status solely from a missing patch. Show known totals versus loaded counts, and an unknown total when the source cannot establish one; source file-list limits never imply a complete PR. A complete patch means the supplied change hunks, not the entire file or unlimited surrounding context. No clone, checkout, raw-file reconstruction, external-diff tool or expanded-context downloader in v1. Show validated file/revision links where available; if exact targeting cannot be established, offer the PR Changes destination with an explicit limitation rather than fabricate a file/line anchor.

   Inline threads attach only when file identity, side/line and recorded revision match known patch coordinates. Missing/ambiguous/old anchors remain available in a labeled discussion list with their source link, including discussions for locally limited or missing patches; never silently drop or relocate them to a current line. Paginate replies independently; partial patch visibility cannot claim complete discussion coverage or mark activity seen merely by selecting a PR/file. Explicit activity destinations follow the already-confirmed seen policy after their destination renders. Access denial purges the resource and its excerpts under the confirmed runtime policy. Full local reading can be unavailable while metadata, permitted discussion navigation and GitHub fallback stay useful.

All three recommendations await human review. After that review, specify virtualization versus accessible paged reading, bounded expanded-thread payloads, responsiveness/memory measurement and fixtures at/above every boundary. These depend on the selected tiers and reading behavior, so they belong to the next round rather than being silently selected now. This ticket has no Answer yet.

### Rendering, accessibility, discussions and performance — proposals only, 2026-10-17

The following four recommendations are new proposals. Numeric targets are intended future acceptance criteria, not benchmark evidence. No library, native behavior or renderer capability is assumed verified.

1. **Bounded rendering.** Use row virtualization for patches and long file/thread navigators, mounting at most 400 patch rows including overscan, and at most 200 metadata rows per navigator. Variable-height inline discussions render in a separately bounded selected-thread panel rather than expanding unlimited Markdown inside diff rows. Preserve file/line identifiers, selection, scroll position and focus within a revision. Parse/index/tokenize away from the UI thread or in cancellable chunks; stop obsolete work when file/head changes. Show plain text with addition/deletion/context markers immediately. Optional syntax color is background enhancement for the automatic tier only; large-tier patches stay plain text. Syntax color cannot delay reading, override the four-color appearance, or become the only indication of a change. DOM child/node and rich-text complexity also require bounds; a visible-row cap alone is not a memory guarantee.

2. **Accessible reading.** Offer a visible, persisted per-user Reading mode choice: continuous virtualized view or paged view of at most 200 patch rows. Both modes can traverse every eligible supplied patch row without increasing approved file limits; paged mode has ordinary semantic content, Previous/Next, current row range and jump-to-hunk/thread controls. Do not detect or force a mode based on assumed screen-reader use. Describe file path, old/new line numbers and added/deleted/context state without relying on color. Keep keyboard focus stable across loading/virtualization; announcing updates must not move focus. Only explicit navigation moves to its destination; before evicting a focused virtual row, preserve it within the mounted-row cap or provide stable focus transfer, never lose focus to the document body. Navigating to an inline discussion selects the separate thread panel and exposes its anchor and return action. Changes of view/page preserve seen-state rules: loading pages and changing PR/file never mark activity seen; only an explicitly opened activity destination marks its corresponding item after rendering. Loading indicators, local-limit/source-limit/error states and partial counts have useful accessible labels/announcements. Require keyboard-only and VoiceOver review at compact/default widths, 200% text zoom and reduced motion; no clipped essential controls or focus traps. Supported long code lines remain horizontally scrollable.

3. **Discussion payload and expansion bounds.** Keep a paginated thread navigator; expand one selected thread at a time in the panel, with at most 20 messages in the current page. Next/Previous replaces the page rather than appending forever. Fetch more only on explicit navigation and obey the existing 100-record/1-MiB IPC limits. Cap each locally displayed message body at 128 KiB UTF-8 and all retained frontend discussion bodies at 2 MiB/100 messages, evicting inactive bodies first. A body above the limit gets an explicit Body too large placeholder and validated source link, without rendering a clipped prefix as complete. Metadata/author/time and permitted navigation stay available. Oversized pages are split into smaller pages within IPC limits; unknown size is not empty content. Retention here concerns frontend memory, not durable Activity/deduplication or backend progress.

   Sanitize Markdown under the existing no-remote-resource/no-embedded-execution policy; display long prose/code lines within a bounded scroll/wrap container. Allow at most 5,000 content DOM nodes across the active message page; downgrade rich formatting to escaped plain text if rich expansion would exceed this bound. If even plain-text layout cannot meet the bound, split the message into explicitly ranged text segments with navigation, preserving the original message identity and source link; no silent omission or bypass of the 128-KiB body limit. Inline and Conversation access share the same retained-body budget. Rendering limits must not truncate backend activity classification or let an incomplete source traversal advance successful progress. An oversized explicitly opened activity destination remains unseen if only a placeholder/source link rendered; normal metadata-only events such as a textless approval can still be complete destinations. This distinguishes an actual rendered destination from merely selecting its placeholder; remote browser reading alone does not mark it seen.

4. **Performance and acceptance evidence.** Propose an Apple M1/8-GiB-class physical Mac as the minimum performance reference, running a supported macOS version to be selected by the packaging ticket. Record exact hardware/OS/app build, window size and collection method. Any different reference must be explicitly reconciled in final acceptance; simulator/browser-only results cannot stand in for native Tauri measurements. On a release build, after five warm-ups, measure at least 30 transitions per tier: 95th-percentile local input feedback within 100 ms, usable automatic-tier cached patch within 500 ms, and usable explicit-large cached patch within 1 second. Patch timing starts at selection/load action and includes cached backend/IPC/parsing/rendering; it ends when navigation and scrolling work, without waiting for syntax color. Include a normal fifty-watch background fixture. Loading/queued/error feedback still meets 100 ms for uncached requests, but network/gh latency is reported separately under confirmed timeouts/deadlines, never counted as a guaranteed remote load time. No app-caused main-thread task above 100 ms in these scenarios, and 95th-percentile frame duration at most 33 ms during a ten-second scripted scroll at the largest accepted patch.

   Measure summed resident memory of Rust plus app-owned WebView/helper processes above the same-build idle-reader baseline. Target at most 200 MiB additional peak resident memory during the reader stress run, with process-attribution method recorded and each measurement compared against the source/row/message/DOM ceilings. Cycle files/threads 100 times, settle for 30 seconds, then repeat; the second settled footprint must be within 20 MiB of the first. This is a measurable reader-regression budget, not an absolute OS memory guarantee or total-app cap. Include every allowed tier, exact/one-over byte/row/line/message bounds, non-ASCII UTF-8, long lines, generated/binary/missing/incomplete patches, many file/thread metadata pages and deeply nested Markdown. Exercise page/continuous mode equivalence, keyboard/VoiceOver line/anchor navigation, selection/head/account/purge races during parsing, focus under virtualization, denied data and source-link fallback. Counters must prove source/model/DOM/message bounds and no stale resurrection. Any missed target blocks performance acceptance; optimize within the approved contract or return for an explicit spec revision, rather than silently increasing limits or lowering the benchmark. No performance or accessibility gate has yet been run.

Await human review of all four recommendations before recording a final Answer. The packaging/reference-OS dependency and native evidence remain visible future gates; they do not reopen settled reading tiers. Production implementation remains out of scope.

## Answer

The reading policy/local limits round and the rendering/accessibility/discussion/performance round are confirmed in full, with the latter amended to **up to 50 discussion messages per page**. The detailed accepted rounds above are the contract; their historical proposal labels no longer indicate open decisions.

- Unified-only selected-file reading, honest source/local/transport/unavailable states, revision-correct threads and safe GitHub fallback. Automatic patch tier: 512 KiB/5,000 rows; explicit large tier: 2 MiB/20,000 rows; logical lines at most 16 KiB. All applicable ceilings are inclusive; no above-hard-limit override, reconstruction downloader or whole-PR patch prefetch. Frontend patch-source retention: 8 MiB/50,000 rows, one active rendered patch.
- Virtualized continuous reading: at most 400 mounted patch rows and 200 metadata rows per navigator. Plain text is usable immediately; syntax enhancement is optional/background for the automatic tier only. Preserve/cancel by revision and selection. Discussions use a separate selected-thread panel. A remembered accessible paged mode shows at most 200 patch rows with semantic navigation, line/change labels, stable focus and no color-only meaning. Require keyboard/VoiceOver, compact/default widths, 200% text zoom and reduced-motion review.
- One expanded selected thread, up to **50 messages per page**, replacing rather than appending pages. Body limit: 128 KiB UTF-8; retained frontend discussion bodies: 2 MiB/100 messages shared across inline and Conversation views. Active message-page content: at most 5,000 DOM nodes, with plain-text/explicit segment fallback under the accepted rules. Existing IPC byte limits can require smaller transfers/pages. Oversized bodies use labeled placeholders/source links; merely opening a placeholder does not mark the activity seen. Reader bounds never truncate backend classification or imply completed source traversal.
- Performance reference: physical Apple M1/8-GiB class, supported macOS to be settled by packaging. Release build, five warm-ups and at least 30 transitions per tier; 95th-percentile local feedback ≤100 ms, usable cached automatic patch ≤500 ms, usable cached large patch ≤1 second, scripted-scroll frame duration ≤33 ms. No app-caused main-thread task above 100 ms in those scenarios. Include normal fifty-watch background activity; report remote latency separately. Reader peak additional resident memory target ≤200 MiB above the same-build idle baseline across Rust/WebView/helpers; repeated 100-cycle stress runs settle within 20 MiB of one another after 30 seconds. Record process attribution and exact hardware/OS/build/method. The accepted detailed boundary/race/accessibility matrix remains required future evidence; a miss blocks acceptance unless fixed or explicitly respecified.
