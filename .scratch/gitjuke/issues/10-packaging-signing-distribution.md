### Platform, release route and executable discovery — proposals only, 2026-10-17

Initial research distinguishes platform capabilities from product choices: Tauri supports separate Apple Silicon/Intel targets and a configurable minimum OS; this does not require GitJuke to support all of them. Developer ID signing/notarization for direct distribution requires appropriate Apple Developer Program access. GUI/login environments cannot rely on shell startup files to locate gh. See the linked research ticket/asset for primary-source facts and uncertainty; nothing here claims a working signed app.

1. **Platform scope.** Apple Silicon arm64 only for v1, minimum macOS 15, no Intel or Rosetta support claim. Use the approved physical M1/8-GiB reference on macOS 15 for the reader benchmark; do not silently replace it with the developer's newer/faster machine. The minimum is a chosen product/test floor, not a Tauri requirement or an assertion that older systems are impossible. Before release, freeze the advertised OS matrix and perform native smoke/lifecycle checks on each advertised major release from that floor; future OS versions are not automatically verified. Dependency incompatibility or unavailable native benchmark evidence blocks the relevant release acceptance or requires an explicit matrix/spec revision. Exact supported patch versions and tested gh versions belong in release evidence, not an untested compatibility promise.

2. **Personal direct distribution.** A personal/direct-install app, outside the Mac App Store, with a Developer ID signed, notarized and stapled DMG containing the app bundle. Copy to /Applications and run there; no privileged installer, bundled gh, package-manager installer or automatic tool installation. Signing access is a future release prerequisite; do not sign up, purchase membership, obtain certificates or publish anything during planning. An unsigned/ad-hoc developer build may be used during later implementation but does not satisfy the proposed distributable-artifact gate, and bypassing Gatekeeper is not the release installation flow. No store listing, broad public launch or hosted service is implied. Signing identity, stable app identifier and version continuity must be fixed before native notification/login/update validation; final identifier selection does not require production implementation now.

3. **Installed-gh discovery.** Propose a saved explicit absolute gh executable path first, then narrowly searched standard installation locations (including /opt/homebrew/bin/gh and /usr/local/bin/gh), then an explicit user file selection if none works. Do not run a login shell, source dotfiles, search project/current-directory executables or silently download/bundle gh. Validate executable/version, retain its resolved path for the session and report the path/version in diagnostics without exposing tokens/private output. A relocated/missing/unusable executable stops remote work/alerts but preserves cached reading; guide the user to repair it and revalidate the configured stable account before resuming. Version text alone is not proof of supported API/stack semantics; exact version/read/schema/provider checks remain acceptance gates. Read published native stack metadata through gh api without requiring a local stack extension. This follows the confirmed read-only/identity contract; it does not promise compatibility with every CLI version or arbitrary third-party stack extension.

All three recommendations await human review. After this round, settle manual versus automatic update UX and schema-aware rollback, precise gh environment/auth-context handling, packaged login/background/single-instance behavior and artifact validation acceptance. These are dependent follow-up decisions, not silently accepted details. Existing pause, opt-in/default-off launch at login, account isolation, migration and alert-attempt policies remain confirmed. No production implementation.

### Updates, gh authentication environment and packaged lifecycle — proposals only, 2026-10-17

These are new recommendations for human review, grounded in [macOS distribution research](../research/macos-distribution.md). They do not reopen the confirmed runtime/identity/pause/notification/reader policies. Exact signing credentials and artifact URLs are later release inputs, not credentials to create or publish during planning.

1. **Manual updates and schema-aware recovery.** No built-in updater, background version check, automatic download/install, update feed or automatic binary rollback in v1. About shows the installed version/build. Distribute a signed DMG with version, release notes, supported OS/gh evidence and checksum through one documented trusted release source designated before distribution; a checksum is not a substitute for platform signing verification. Updating means explicit Quit (window close is insufficient), replace /Applications/GitJuke.app, then relaunch. Preserve application data, account binding, saved executable/config paths, baseline/attempt/seen ledgers, settings, Pause and login preference. Revalidate executable, identity and supported schema before monitoring; use the confirmed bounded recovery after the update, not historical replay.

   Each release declares its readable/upgradable schema range. A downgrade is supported only if the older binary explicitly accepts the existing schema; no automatic downgrade migration, database restore or deletion. An incompatible binary stops without modifying the newer database and explains that a compatible/newer corrective release is required. Prefer a forward corrective build. Existing transactional migration failure behavior and explicit destructive recovery reset remain unchanged; restoring an old database cannot be promised to preserve alert-attempt/deduplication history. Interrupted replacement, insufficient disk and failed validation must leave original data preserved and monitoring stopped if a valid app/schema cannot be established. Reinstalling the compatible app does not imply resetting data. Removing the app leaves local data; deliberate destructive recovery is separate and explicit.

2. **Deterministic stored-gh authentication context.** Use existing stored gh credentials/configuration, with no app credential store, token entry/import/export, scope changes or account switching. Build a deliberate child environment, rather than blindly inheriting the launch environment: default to <OS-account-home>/.config/gh independent of shell dotfiles/XDG overrides, with an explicit advanced absolute gh-configuration-directory option for an intentional custom context. Supply this selected directory as GH_CONFIG_DIR. Display the selected executable/configuration directory and non-secret configured account identity in diagnostics. Never copy token values into diagnostics or persistent state. An explicitly selected config context is reused on Finder/login launches; changing it must pass the same bound stable-user identity check and cannot silently import a different account. Switching context invalidates pending jobs before revalidation.

   Do not pass inherited GH_TOKEN/GITHUB_TOKEN or enterprise token equivalents, GH_HOST/GH_REPO, GH_CONFIG_DIR/XDG_CONFIG_HOME overrides, pager/editor/browser overrides, or arbitrary shell/developer injection variables into child reads. Supply the selected/default configuration context explicitly, explicit github.com/repo parameters, prompt-disabled/noninteractive settings and a narrow system PATH for required helpers. Preserve needed OS-account/locale/keychain context and documented proxy/custom-CA networking settings without exposing their possibly sensitive values; exact allowlist belongs to transport implementation/verification, not a general shell API. Do not source shell startup files. If override variable names are detected, explain that GitJuke uses stored gh login and its selected config context; never display the values or silently equate ignored overrides with expired credentials. Environment-token-only authentication is unsupported in v1; offer instructions to establish stored gh authentication externally. Parse auth-status JSON fields and verify the stable identity through a bounded authenticated read; exit status or username alone is insufficient. Distinguish missing CLI/config-context mismatch, missing/locked credentials, identity mismatch, unsupported command/schema and denied resource. Preserve the confirmed account lock, generation/discard and no-automatic-switch rules.

3. **Packaged login and process lifecycle.** Use the documented Tauri LaunchAgent route to start the same installed app process in background/menu-bar mode only after explicit login opt-in. Register only the stable /Applications/GitJuke.app location; a DMG/download/translocated or moved copy gives install/repair guidance and does not create a login registration or a second monitor. Login starts without opening the reader or requesting notification permission; setup/auth errors remain visible in the menu bar and open into actionable reader guidance on user action. First normal manual launch opens setup/reader. Manual reopen or a notification click activates the existing instance/window rather than creating another scheduler/store writer. Enforce a single monitor instance across simultaneous login/manual launches. Preserve Pause on all starts; permission denial does not stop otherwise authorized monitoring. Window close retains the agreed background/watch behavior.

   Explicit Quit stops scheduling, cancels/reaps owned children and exits; no KeepAlive watchdog/daemon or automatic crash relaunch. Quit does not disable the explicit login preference: next user login may start it again. OS-disabled login registration is shown as disabled/unavailable rather than silently re-enabled. Enable/disable failures are reported honestly; after manual replacement or a moved app, verify actual registration/path before claiming login launch works. Repair/re-registration requires an explicit user action if OS/user state disabled or invalidated it. Sleep and offline behavior remain the confirmed cached-reading/bounded-recovery contract, without an OS wake/delivery guarantee.

4. **Stable artifact identity and native acceptance.** Propose app/display name GitJuke, installed bundle /Applications/GitJuke.app and stable bundle identifier dev.hmrguez.gitjuke for personal v1. Use monotonic release/build identifiers; keep the bundle identifier and intended Developer ID team continuous across updates. Actual Developer ID Team ID/certificate access, release-source location, signed artifact checksum and tested OS/gh version matrix must be recorded before distribution, not invented as evidence or provisioned now. Unsupported signature/team/identity changes are not transparent upgrades; they need explicit requalification of permissions/login/data-location continuity. Keep release credentials outside repo/app data.

   Required evidence on each advertised macOS major: download/quarantine Gatekeeper acceptance without bypass, stapled offline first launch, arm64 execution/minimum-OS rejection where applicable, external gh/keychain access from Finder and login without a terminal, default and explicit custom config contexts, ignored-token overrides without secret leakage, locked/missing credentials and account mismatch, supported API/native-stack fixture and CLI version reporting. Exercise installed/mounted/moved bundle paths, default-off login setup, enable/disable and OS-disable/failure states, login without reader UI, duplicate launch suppression, reopen/notification-click routing, permission denial, close versus Quit, no orphan child, preserved Pause, sleep/offline recovery, and manual replacement with login registration intact or explicit repair. Validate compatible upgrade/downgrade, rejected newer schema, failed/interrupted migration/replacement and low disk without history reset or replayed attempted alerts. The physical M1/8-GiB/macOS-15 reader performance baseline remains required. All evidence is pending; UI fixture/build checks cannot satisfy it.

Await human review of all four branches. No production app, signing, login registration, auth operation, updater or release publication has been implemented or performed by this round. Final acceptance still waits for this ticket to resolve.

## Answer

Resolved 2026-10-17 through human review. Both the platform/release-route/executable-discovery round and the updates/authentication/lifecycle/acceptance round above are confirmed in full. Their detailed accepted recommendations are the contract:

- Apple Silicon arm64 only, minimum macOS 15; physical M1/8-GiB on macOS 15 remains the performance reference. Qualify each advertised OS major and record exact patch/gh evidence before claiming compatibility. Personal direct Developer ID signed, notarized and stapled DMG, installed as /Applications/GitJuke.app. No Intel/Rosetta, store, privileged installer or bundled/automatically installed gh scope.
- App name GitJuke, stable bundle identifier dev.hmrguez.gitjuke, monotonic release/build identifiers and intended Developer ID team continuity. Actual signing access/team, trusted release source, checksum and tested matrix must be established before distribution; they are not invented by this resolution. Signing-team/identity changes need explicit continuity requalification.
- Manual update only: explicit Quit, replace the app, relaunch and revalidate executable/account/schema. No background update checks, feed, automatic download/install or binary rollback. Preserve app data/settings/Pause and durable activity/seen/attempt/progress history. Older binaries run only against their declared supported schema range; otherwise stop without modifying data. No automatic database restore/downgrade/reset. Prefer a forward corrective release; removing/replacing the app does not remove/reset its data.
- Discover installed gh through saved absolute path, known installation locations and explicit file selection, without a shell or project-path search. Validate/display version/path and retain the resolved executable. Use stored gh authentication and explicitly supply GH_CONFIG_DIR, defaulting to <OS-account-home>/.config/gh or the selected advanced absolute custom directory. Strip inherited token/host/repo/config overrides and apply the accepted noninteractive child-environment contract. Token-only environment authentication is unsupported in v1. Never print/import/export credentials or alter scopes/accounts. Context changes invalidate pending work and must validate the existing bound stable identity; diagnostics distinguish config/auth/CLI/schema/access failures.
- Opt-in/default-off LaunchAgent starts the same installed app in menu-bar mode without opening the reader or prompting permissions. Single-instance activation handles manual/login/notification launches. Only the installed stable app path is registered; moved/DMG copies receive guidance. Explicit Quit cancels/reaps children and stops the app without disabling next-login preference. No watchdog/automatic crash relaunch. Respect OS/user-disabled registration and require explicit repair where invalidated. Preserve Pause and existing permission/close/sleep/offline semantics.
- The detailed packaged native matrix above is required future acceptance: downloaded/quarantined/offline signed launch, OS/architecture qualification, Finder/login gh/keychain/default/custom config and override handling, account/permission failures, published-stack compatibility, registration/duplicate-launch/window/notification/Quit behavior, update/schema/disk/interruption recovery and no durable-history reset or ambiguous-attempt replay. Existing fixture UI evidence does not satisfy these gates.

No packaging policy decision remains open. Signing/provisioning/build/publication, gh auth/API operations, native lifecycle and performance validation have not been performed by this planning work. The only remaining decision ticket is [Settle specification handoff and release acceptance](11-final-acceptance.md), now unblocked. Do not claim or resolve it as part of this resolution. Production implementation remains out of scope for the planning effort.
