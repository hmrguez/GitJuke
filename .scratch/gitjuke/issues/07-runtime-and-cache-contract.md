### Runtime/cache review round — proposals only, 2026-10-17

Notification policy is now resolved; this ticket is claimed and unblocked. Confirmed constraints remain Tauri + React, Rust invoking installed gh for every GitHub read, single GitHub.com account, continued monitoring after window close, and read-only GitHub behavior.

1. Ownership: one Rust-owned application runtime owns gh process execution, scheduling, cache writes, activity classification, native delivery and menu-bar lifecycle. The React window is a client of typed commands/cache-revision events, not a second scheduler/store. Closing the window leaves the same app process running; no separate daemon or hosted service. Reopening reconstructs from the authoritative backend state. Runtime structure/module names remain implementation choices; no frontend arbitrary shell API.
2. Persistence: one transactional SQLite store in the macOS application-data location holds app-owned durable state, separating disposable fetched content from settings, saved queries, seen/deduplication records and successful sync/recovery progress. Cache eviction must not erase preferences, mark unseen activity seen, reset baselines, or cause historical alerts to replay. React holds only presentation state such as open tabs/scroll positions and does not become an independent durable source. No gh tokens in the store; use existing gh authentication. Retention limits, sensitive-content purge behavior, cache-rebuild guarantees and backup/export scope require the next round. No claim of app-level encryption yet.
3. Identity boundary: bind GitHub-derived records/progress to github.com plus the authenticated user's stable ID; check identity before starting/restarting a session and dispatching authenticated work. An observed identity mismatch/auth loss stops new remote work and native delivery; discard stale in-flight results and hide the previous account's private content. Offer guidance to restore the configured account in gh; never switch credentials automatically or import the new account. Keep existing local state for the original identity. Appearance can remain available. A deliberate replacement-account/reset flow is not implied; one account remains the product scope. There is no absolute guarantee against an external gh identity change racing an already-running subprocess; generation checks/discard behavior and verification belong in the transport design.

Next rounds after these choices: discovery cadence and scheduler fairness/bounds; stale results and per-resource completeness; retention/clear-cache behavior and access loss; durable activity/recovery/delivery semantics across crashes. Native OS alert delivery cannot share a transaction with the database, so its crash trade-off must be made explicit rather than promising exactly-once delivery.

### Discovery, retention, stale data, and crash recovery — proposals only

1. Discovery and scheduling: reconcile authored/direct/team-request membership every 60 seconds while monitoring is enabled, awake/online and budget-safe, and on startup/resume/recovery when due. Refresh active PR/check snapshots on the confirmed ten-second target; poll notification discovery on its independent X-Poll-Interval deadline. Reconcile an opened saved-query view every 60 seconds, with selected detail hydrated on demand; inactive saved queries do not run background searches. User-triggered refresh requests priority but cannot override server deadlines/backoff. One serialized gh queue, selected-user work first, with aging/fair rotation so background membership/notification jobs are not starved; no overlapping cycles or replayed ticks. Sixty seconds is a scheduling target, not a source-indexing/delivery guarantee; quota pressure visibly delays it. Team membership lookup can be reused until reconciliation invalidates it; exact cache invalidation and measured batching are transport details, not a new freshness guarantee.
2. Retention: cap disposable fetched content at 500 MiB with least-recently-used eviction and a 30-day maximum since last successful refresh/access. Do not persist check log bodies. Keep Activity records for 90 days from source occurrence, including unseen records, with an explicit retention notice; expiration removes records rather than marking them seen. Active-watch identities, settings/queries, successful progress and compact deduplication/alert-attempt/seen ledgers are outside content eviction and survive restart and Clear downloaded content. Retain identity-only ledgers until a deliberate local-data reset; no automatic deletion that could replay historical alerts. Clear downloaded content removes cached PR bodies/diffs/conversations and may require online refetch; it preserves monitoring identities/configuration/activity ledgers. No export/backup UI or additional app-level encryption in v1; rely on the local OS account protections, with no claim that this encrypts the database. Exact SQLite on-disk overhead/compaction limits must be specified before calling total app storage bounded: 500 MiB is the disposable-content budget, not a whole-database cap.
3. Stale data: retain readable cached content for offline/timeouts/rate limits, with per-resource last-successful-fetch time, completeness and error reason. A partial/failed refresh must not replace complete data with empty data, advance successful progress, clear unseen state or remove membership. Head changes invalidate current diff/check associations; revision-specific old content may be shown explicitly as old, never as current or re-anchored to new lines. Explicit resource access-denied/not-found responses hide and purge cached bodies/diffs/conversation/log content for that resource, retaining minimal identity/progress/unseen metadata and an unavailable placeholder; do not interpret 404 as confirmed deletion or remove watch reasons on that evidence. No successful-empty claims for inaccessible sets. Global authentication loss/mismatch follows the already agreed identity lock; a permission error for one resource does not automatically lock unrelated accessible PRs. Recovery restores content only after successful authorized reads.
4. Crash recovery: atomically persist ingested source activity, deduplication/seen state, successful pagination progress and native-alert intents before delivery; incomplete pagination keeps staged progress separate until traversal succeeds. Persist an attempt marker before calling the OS. If a crash leaves delivery ambiguous, do not resend that attempted alert: favor avoiding duplicate native alerts, accepting that an OS alert can be missed while its Activity record remains durable. Unattempted intents can recover under existing grouping/privacy/permission/seen policies. Do not promise exactly-once OS delivery or infer user seen state from delivery. Resume completed progress and bounded catch-up after restart; preserve pause. If the database is corrupt/unmigratable, preserve it, stop monitoring and offer recovery instead of silently resetting baselines/replaying history. No record is promised durable before its transaction commits.

All four proposals await the human. Revisit storage/ledger bounds, discovery endpoint coverage/budgets, alert-intent state transitions, cache revisions and schema-migration validation before resolving this ticket. Production implementation remains on hold.

### Implementation-readiness review — proposals only, 2026-10-17

The existing claim by hmrguez continues. All confirmations above stand. The following are new recommendations for human review, not an Answer or approved contract. Numeric bounds are initial design limits to validate, not measured capacity or upstream API facts.

1. **Transport and queue bounds.** One gh child at a time, including identity probes; argument arrays and stdin only, fixed read operations, explicit host, no shell interpolation or interactive prompts. Resolve and retain the installed executable path for the session. Give each child a 30-second wall deadline, 16 MiB stdout ceiling and 64 KiB stderr ceiling, enforced while streaming. On timeout, overflow or cancellation, terminate its owned process group, allow at most two seconds for graceful exit, then kill/reap before another child starts. Never parse truncated output as success; retain safe cached content and expose the failed/partial resource. Do not automatically retry an unchanged oversized request: reduce the batch/page where possible, otherwise show a bounded-content limitation and GitHub link. Detailed large-diff policy remains a separate decision.

   Materialize at most 128 runnable descriptors in memory; coalesce duplicate refreshes by identity/resource/revision, retain outstanding due state in the store, and expand pagination one page at a time. No per-tick backlog and no cap on watch membership. A full queue defers work rather than losing watches/progress; explicit user requests receive a visible queued/busy result. At each child completion, choose work again; after at most three selected/user jobs run the oldest eligible background job, rotating watches fairly. Priority never bypasses server deadlines, quota or backoff. Check-log reads are explicit, memory-only, bounded by the same transport ceiling, and released on leaving the log view, locking the account or closing the reader. Bound IPC too: page lists at 100 records and 1 MiB per response; oversized detail content needs chunked access or an explicit limited state, never silent truncation. Process/IPC limits are independent of the pending large-diff rendering limits.

2. **Cache revisions and stale results.** Every job carries the configured account identity/session generation, resource generation, and applicable head SHA or saved-query version. Commit only if these still match. Account lock, access purge and Clear downloaded content invalidate generations so late children cannot resurrect hidden/cleared content; restoring access requires a new authorized read. New-head results cannot be overwritten by an older head. A late result for an unselected PR may still populate its matching cache, but cannot change selection or mark Activity seen. Resource snapshots carry fetch time, completeness, error, source revision and a monotonically increasing committed store revision. Publish events after commit as invalidation hints; React reads authoritative snapshots, ignores older responses and re-reads on reopen/reconnect, so a lost event cannot strand the UI. Multi-page traversals stage against a generation and only publish complete membership/progress on success; partial detail may be exposed separately with explicit labels. Changes observed across a mutable traversal require reconciliation; pagination is not a source-wide atomic snapshot. Obsolete staged traversals are disposable and bounded within the content budget. Native-alert intents are revalidated for identity, pause, permission/category, seen/deduplication and current head before an attempt; an invalidated intent is suppressed without marking Activity seen. These checks preserve the previously confirmed ambiguous-attempt/no-replay rule.

3. **Durable growth and SQLite management.** Keep the approved identity-only ledgers indefinitely; do not introduce a hard size cap that silently drops deduplication/progress or resets the baseline. Compact terminal alert-intent payloads and expired Activity bodies to the minimum identity/outcome metadata needed to prevent replay; do not retain bodies/previews in those ledgers. The 500 MiB content budget includes staged downloads and retained Activity payloads; the 90-day Activity rule is a maximum lifetime, not a promise of unlimited payload storage. Preserve a minimal Activity entry and unseen state throughout its retention window if its fetched payload is evicted. Resource-denial purge also removes associated Activity excerpts, while retaining safe identity/progress metadata. No persisted check logs.

   Report total managed database/WAL/temp bytes separately from the disposable-content budget. Propose a storage warning at 1 GiB total and a protective stop of remote ingestion/native dispatch when available disk falls below 1 GiB or a storage write/checkpoint fails; thresholds are configurable implementation constants, not a whole-database guarantee. Preserve cached reading, settings and pause; retry only after storage is healthy. Never dispatch an alert whose durable attempt marker could not commit. Reuse freed database pages, checkpoint WAL at safe idle boundaries, and perform bounded incremental reclamation; do not run an unbounded startup VACUUM. Account for temporary migration/maintenance space before beginning. The ledger can grow over years: expose its size and explain that Clear downloaded content cannot remove it. A destructive reset is an explicitly confirmed recovery action with a new historical baseline and no historical native alerts, not automatic maintenance.

   **Open policy interaction:** previous confirmations specified a 500 MiB disposable-content budget and 90-day Activity retention without deciding whether Activity payloads share that budget. The allocation and minimal-entry proposal in this paragraph requires explicit approval; it is not an interpretation already confirmed.

4. **Migration and recovery acceptance.** Version the schema; run supported upgrades transactionally before scheduling or alert delivery, with sufficient disk space and the configured identity locked until validated. A failed/interrupted upgrade must reopen the previous committed schema or stop with the original files preserved. A newer unsupported schema must stop without modifying it. Corrupt/unmigratable state offers a recovery explanation and explicit local reset; no silent database replacement, baseline loss or automatic historical replay. No new export/backup UI is implied. Storage-health recovery resumes bounded reconciliation under the existing pause/deadline rules.

   Required runtime evidence: kill/restart around ingestion, progress commit, intent creation, pre-dispatch attempt marker and post-dispatch return; incomplete pagination; 129+ pending jobs; a hung/oversized child; continuous selected refresh versus background fairness; head/query/account changes during a read; denial/clear followed by late completion; missed/reordered UI events; 500 MiB eviction and 90-day expiry including unseen entries; warning/low-disk/write/checkpoint failure; and interrupted/failed/successful migration plus future/corrupt schema. Verify no orphan child, false successful-empty set, stale-content resurrection, lost durable seen/deduplication state, replayed ambiguous attempt, or silent watch removal. Measure the fifty-watch target with real authorized API/native fixtures later; fixture UI checks do not satisfy these gates.

Review these four independent branches with the human before resolving this ticket. Large-diff thresholds, supported macOS/architectures, signing/distribution/update policy and final release acceptance remain beyond this ticket; sharpen them into named decision tickets as their prerequisites settle. No production implementation or new ticket resolution in this review round.

## Answer

Resolved 2026-10-17 through human review. The confirmed runtime contract consists of the detailed ownership/persistence/identity round, discovery/retention/stale-data/crash-recovery round, and implementation-readiness round above, each explicitly accepted by the user. In particular:

- One Rust-owned runtime and transactional SQLite store serve typed React clients and the menu bar. GitHub data is isolated by stable configured account identity; detected mismatch/auth loss stops remote work and alerts and hides prior private content. All GitHub access uses installed gh through fixed read operations.
- Discovery remains at the confirmed 60-second membership/open-query targets, ten-second active PR/check target and server-directed notification interval. One gh child at a time, 30-second wall deadline, 16 MiB stdout/64 KiB stderr limits, two-second termination grace, then kill/reap. Coalesced runnable queue: 128 descriptors, with persisted due state and fair service after at most three foreground jobs. No watch-membership cap or lost-work tick backlog. IPC list pages: at most 100 records and 1 MiB per response; chunk or visibly limit oversized details. Check logs are bounded and memory-only.
- Account/resource/query/head generations guard commits, including late completion after account lock, access purge and Clear downloaded content. Post-commit revision events are invalidation hints; React rereads authoritative snapshots. Partial traversals cannot publish complete membership/progress. Alert intents are revalidated before recording an attempt; ambiguous attempts are never replayed. This can miss a native alert while preserving committed Activity.
- The 500 MiB disposable-content budget includes staged downloads and Activity payloads. Disposable content has the approved 30-day untouched expiry; minimal Activity entries and unseen state survive payload eviction for the 90-day Activity window, including unseen entries. Resource denial also purges Activity excerpts. Compact identity-only seen/deduplication/alert/progress ledgers persist until deliberate reset; no total-database size guarantee. Warn at 1 GiB managed storage and stop ingestion/native dispatch below 1 GiB free disk or on write/checkpoint failure, preserving cached reading/settings/pause. Use bounded reclamation and safe checkpoints; no unbounded startup VACUUM. No export/backup UI or extra app-level encryption.
- Versioned transactional migration precedes scheduling/delivery. Failed/interrupted migrations preserve the prior committed state or stop with original files preserved; future schemas stop without modification. Corrupt/unmigratable databases never silently reset. Explicit destructive recovery reset establishes a fresh historical baseline without historical alerts. Preserve pause and normal recovery/deadline behavior.

No runtime/cache policy decision remains open. The detailed fault/recovery matrix in the implementation-readiness round is required future evidence, not a claim that these behaviors have been implemented or verified. Numeric limits are approved initial design bounds, not measured capacity. Fifty watches remains a validation target. Authenticated API compatibility, quota/payload measurements, migrations and native desktop behavior remain unverified acceptance gates.
